## 🧭 Where it stands — 2026-10-29

### Track 1: LDMs on the page categories

- **11 labels**, defined in [`docs/reference/categories.md`](../../docs/reference/categories.md). The order of `CATEGORIES` in `model_registry.py` is bound to the checkpoints and must not change.
- **Comparable baseline:** the **fold-1 test partition (4,795 pages)**, held out for both `v1.4` (EfficientNetV2-M, 95.87 % top-1) and `v4.4` (RegNetY-160, 95.81 %). The two do not differ significantly (exact McNemar). The ±0.6-point 95 % interval sets the smallest gap worth reporting. About a quarter of each fold's test pages come from documents with other pages in training; results.md reports the unseen-document figure separately (95.60 / 95.19 %).
- **Known hard pairs:** `TEXT_T` → `TEXT` (recall 87–92 %), `LINE_HW` → `LINE_T` (4–9 %). Top-3 covers 99.75–99.90 %. An LDM is worth something here only if it separates these pairs, or gives better-calibrated low-confidence flags.
- **Candidates:** Cloudflare's `Clef` (27B) and `Clef-Flash` (9B), plus `Clef-omni`. Pin the revisions. The Clef card was tested with PyTorch 2.11 / `transformers` 5.10.2, while this repository pins 2.7.1 / `<5`, so the experiment runs in a separate environment.
- **Extended set:** the UPD now names the first concrete "further processor": the image describer of track 2, for `PHOTO`, `PHOTO_L`, `DRAW` and `DRAW_L` pages.

### Track 2: structured description of archive images (new)

| Target (body)                                | Output field (proposal)                                                    | Kind of answer               |
|:---------------------------------------------|:---------------------------------------------------------------------------|:-----------------------------|
| 1–2. Made during a dig, or in a lab after it | `capture_context` ∈ {`dig`, `post_dig_lab`, `other`, `unknown`}            | closed choice (suits an LDM) |
| 3. OCRed labels on the image                 | `labels[]`: text, plus key-value pairs when the label is structured        | generative + OCR             |
| 4. Number of objects                         | `object_count_pattern` ∈ {`1`, `N`, `1a…1n`}, with the count               | closed choice + number       |
| TODO: description by vocabulary              | `description` + `terms[]` from the controlled vocabulary                   | generative, constrained      |
| TODO: labelled object segments               | `objects[]`: bbox or polygon + vocabulary term (+ instance id for `1a…1n`) | grounding (needs a VLM)      |

- **Prompt machinery to reuse:** keyword-extract's `prompt_template.py` with its `[[block]]` text file (`prompts/system_prompt.txt`, blocks switched by config flags), the JSON output template (`prompts/output_template.json`), and the vocabulary in `data_samples/vocab/union_nested.json`. Its facets include Artefact, Material, Feature, Finds Context, Methods and Chronology.
- **Vocabulary gap:** the vocabulary has photography and field-work terms ("fotografická dokumentace", "terénní archeologická dokumentace") but nothing for "made in a lab". `capture_context` therefore needs a small new controlled list.
- **Linked document:** optional context. It can contain the answer (for example, a caption that names the lab), so every run is scored both with and without it.
- **No record home:** the shared record has no block for image descriptions, regions or object segments (`forms` is owned by keyword-extract and holds fixed-field values). This is the same gap as atrium-project#22's "image regions" check. Outputs stay experiment JSON until a schema proposal goes through atrium-project#71.
- **Gold:** none for any track-2 field. It needs a small annotated set from `PHOTO*`/`DRAW*` pages, made by ARÚP/ARÚB annotators. Predictions are never used as gold.

### Hardware (body TODO)

- An **NVIDIA DGX Spark**-class unit has **128 GB of unified memory**, and two units can be linked. Its memory bandwidth (~273 GB/s) makes dense 100 GB+ models slow to decode. MoE models with few active parameters fit better. _Check these figures against the current NVIDIA specification._
- Rule of thumb: weights ≤ ~100 GB on one unit, leaving room for the KV cache and image tokens. A "100–150 GB" model means either two linked units or a smaller quantisation.
- **Shortlist to verify at run time** (weights ≈ parameters × bytes per parameter):

  | Model                 | Total params | Precision | Weights  | Fit on one unit     |
  |:----------------------|-------------:|:----------|---------:|:--------------------|
  | Clef-Flash            | 9B           | bf16      | ~18 GB   | yes                 |
  | Clef                  | 27B          | bf16      | ~54 GB   | yes                 |
  | Llama 4 Scout         | 109B (MoE)   | FP8       | ~110 GB  | tight               |
  | GLM-4.5V              | 106B (MoE)   | FP8       | ~106 GB  | tight               |
  | Qwen3-VL-235B-A22B    | 235B (MoE)   | 4-bit     | ~120 GB+ | two units, or tight |
  | InternVL3.5-241B-A28B | 241B (MoE)   | 4-bit     | ~125 GB+ | two units           |

- **Also available:** the Grace Hopper machine via Viktor, for very large VLMs such as MiniMax-M3-MXFP8 in vLLM (stranak on atrium-project#22, 06-19).

## ⚠️ Limits

- Artificial Analysis' Decision Index is a general benchmark. Only local results on archive pages decide anything.
- Use Clef's typed decision interface and keep the per-option probabilities, invalid outputs and timeouts. Do not parse free text into labels.
- Hosted inference needs a data-governance check before any archival image leaves the cluster.
- Extended labels must map to a documented processor action. No production taxonomy, registry, API or default changes in this issue.
