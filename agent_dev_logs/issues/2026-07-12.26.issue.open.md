## What the uwebasr-skill pattern actually is 🔍

### https://github.com/honzas83/uwebasr-skill

It's deliberately minimal — four things:

1. **A zero-dependency Python client script** (`scripts/uwebasr.py`, stdlib only, optional `ffmpeg`) that wraps a hosted REST API. No pip install, no venv — an agent can `curl -O` the single file and run it.
2. **A `SKILL.md` with YAML frontmatter** (`name` + `description`) followed by structured *agent guidelines*: model-selection strategy, when to ask vs. guess, default output formats, and explicit error-handling playbooks (e.g. "on HTTP 503 retry; if it persists, tell the user the backend is busy").
3. **Multi-agent install instructions** — the same repo works as a Claude Code skill (`~/.claude/skills/`), Codex skill (`~/.codex/skills/`), and Antigravity context via `AGENTS.md`.
4. **Citations baked in** — CLARIN/LINDAT acknowledgements and papers to cite, which matters for an academic service.

The key insight is that the skill is a *client*, not the service — all the heavy lifting stays on LINDAT infrastructure, and the skill is just curated knowledge about how to call it well.

## Why `atrium-page-classification` maps almost 1:1 ✅

You already have every ingredient the ASR skill has:

- **A hosted-style REST API exists** — `service/api.py` (FastAPI) with `/predict_image`, `/predict_document` (multipage PDF), and `/info`, plus the `frontend-lindat` variant clearly aimed at LINDAT deployment. That's the exact analogue of `uwebasr.zcu.cz`.
- **A model-selection story an agent needs guidance on** — the `v1.x`–`v5.x` revision matrix (ViT/EffNet/RegNetY, base sizes, dataset generations) is precisely the kind of "which model do I pick" knowledge SKILL.md exists to encode. The ASR skill's "prefer zipformer, use MALACH for oral history" section translates directly to "prefer `v4.3`/best-5 ensemble, use `-tn 5` for ambiguous pages, categories mean X."
- **Structured output** — top-N predictions in tabular/JSON form ≈ their format-selection guidelines.
- **Citation/acknowledgement material** — `CITATION.cff`, ATRIUM funding badge, LINDAT dataset handle already exist.

## Proposed shape 📐

A separate lightweight repo (or `skill/` subdir, but separate repo matches the reference and keeps the clone tiny):

```
atrium-page-classification-skill/
├── SKILL.md            # frontmatter + agent guidelines
├── README.md           # human-facing install (Claude Code / Codex / Antigravity)
├── LICENSE             # MIT, matching parent
├── requirements.txt    # empty/informational, zero-dep goal
└── scripts/
    └── atrium_classify.py   # stdlib-only client for the REST API
```

Client design decisions worth copying:
- **stdlib `urllib` + `mimetypes` multipart upload** — no `requests`, so the "download one file and run" story holds
- **`--format` flags** mapping to what the API returns: per-page top-N table (CSV), raw JSON, and maybe a `--best`-style summary
- **Retry-on-503 with a clear agent-facing failure message**, mirroring their error playbook

SKILL.md agent guidelines section would encode things only you/DanaKriv know:
- category semantics (🪧 Text/Drawing/Table/…) and when top-3 vs top-5 matters
- "don't guess on ambiguous archival material — surface top-N with scores instead of asserting top-1" (the issue #15 lesson that ~24/229 ambiguous samples flip between model generations is *exactly* the calibration knowledge an agent should carry)
- PDF vs PNG input routing (`/predict_document` vs `/predict_image`)
- paradata note: server-side inference is logged via `atrium_paradata.py`, so provenance is preserved even when an agent is the caller — a nice ATRIUM-specific selling point the ASR skill doesn't have

---

Given LINDAT isn't live, a branch that bundles **server + client + skill wrapper** is actually the more honest packaging: the agent can't rely on a public endpoint, so the skill must know how to *stand up* the server itself, then talk to it as a client. That's still a clean server–client architecture, just with a local lifecycle section added.

## What the branch needs to contain 🧩

I checked the live `test` HEAD dependency graph: `service/inference.py` does `sys.path.append(parent)` and imports `classifier.py`, `ensemble.py`, `model_registry.py` — and `classifier.py` pulls in the full torch/transformers/timm stack. So the server side can't be pruned much below:

```
skill branch (e.g. `skill`)
├── SKILL.md                     # 🤖 frontmatter + agent guidelines (the new core)
├── README.md                    # trimmed: skill install + server setup only
├── LICENSE / CITATION.cff
├── scripts/
│   ├── atrium_classify.py       # 🪶 NEW: zero-dep stdlib client (urllib multipart)
│   └── serve.sh                 # thin wrapper: venv/docker up, health-wait on /info
├── service/                     # unchanged: api.py, inference.py, requirements.txt
├── classifier.py, ensemble.py, model_registry.py, utils.py   # server deps
├── atrium_paradata.py, para_licenses.py                      # provenance intact
├── setup/                       # config.txt, para_config.txt, setup_api_service.sh
├── Dockerfile, docker-compose.yml, docker-compose.gpu.yml
└── run.py                       # only for model download (--hf), documented as such
```

Dropped relative to `test`: `data_scripts/`, training/eval paths in docs, `parallel_best.py`, `yolo_classifier.py`, sweeps, `tests/` (or keep a minimal client-side test), `agent_dev_logs/` (stays on `test`/hub), `small_data_samples` (maybe keep 2–3 images as smoke-test fixtures — actually useful for the skill's self-verification step).

## The server–client split in SKILL.md 🔌

The skill teaches the agent a **two-phase workflow**, which is the main structural difference from uwebasr-skill:

**Phase 1 — ensure server is up:**
1. `GET {base_url}/info` (default `http://localhost:8000`) — if it answers, skip to phase 2.
2. Otherwise start it: prefer `docker compose up -d` (CPU) / `docker-compose.gpu.yml` (GPU), fallback `setup_api_service.sh` + `uvicorn`. First run downloads model weights from HF (`ufal/vit-historical-page`) — SKILL.md must warn about download size (~300 MB–1.2 GB per revision) and startup latency so the agent doesn't declare failure prematurely.
3. Poll `/info` until healthy, with a timeout playbook (analogue of their 503 guidance).

**Phase 2 — classify (pure client):**
- `python3 scripts/atrium_classify.py page.png` → `/predict_image`
- `python3 scripts/atrium_classify.py doc.pdf` → `/predict_document`
- `--base-url` flag with `ATRIUM_PC_URL` env override — so the *identical* client and guidelines work unchanged the day kosarko's LINDAT deployment exists; you'd just flip the documented default. That's the payoff of keeping strict client discipline now.
- `--model vX.Y`, `--top-n N`, output as CSV table / raw JSON.

The client stays stdlib-only (multipart via `urllib` + boundary construction by hand, like the ASR script) — the heavyweight deps live entirely behind the API.
