## Strategic actions

### A — Run the one check that has never actually executed
`docker-build-smoke` — the job that `docker run`s the built image, polls `docker inspect
--format='{{.State.Health.Status}}'` for `healthy`, curls `/health` and `/ready`, then `docker
stop`s it and asserts a clean exit — is gated `if: github.event_name == 'pull_request'` in the hub's
`docker-tool.reusable.yml`. `f1df2c5` landed via a **direct push to `test`**, so that job shows
`skipped` in CI run `34150657998`, not `success`. Every other check the two build-and-push jobs
run (build, Trivy, publish) passed — but the specific thing #49 exists to verify (the `HEALTHCHECK`
directive points at a real, working probe; `SIGTERM` actually drains cleanly) has not been machine-
checked on this repo's real image yet. Open a PR that touches this repo (even a no-op one) to
trigger `docker-build-smoke`, or `docker pull` the published `:test-api` tag locally and run the
five-step check by hand; either way, record the result in this issue before closing it.

### B — Check off the issue's own checklist and close
Once A is confirmed, tick all nine boxes in the issue body (they are currently unchecked despite
being implemented) and close #49 with a comment naming the CI run and/or the manual verification
that confirmed the container-level behavior — not just "the code is here."

### C — Leave the parent open
Do not treat #49's closure as closing atrium-project#55. The hub issue's acceptance criterion is
ARÚP/ARÚB confirming behavior on their own Kubernetes (`docs/k8s_acceptance_runbook.md` in the
hub), which is out-of-band from this repo's CI by design and unrelated to whether this checklist
is ticked.
