# Strategy — Issue [#58](https://github.com/ufal/atrium-page-classification/issues/58): Experiment with LDMs (Large Decision Models) with current and extended categories

> _Refreshed **2026-10-29** for the body edit of 16:58 UTC, against `v1.12.1-beta` (`b9ebd7d`). Drafted 2026-10-20 at `0f9ae3e`. No comments or experiment outputs exist yet. Summary: [`../digests/58.digest.md`](../digests/58.digest.md)._

**Status**: 🧪 **Exploratory, two tracks, design and feasibility first.**
- **Track 1:** can decision models classify page images usefully on the 11 labels and on a processor-aware extension?
- **Track 2 (new):** can a VLM prompt, built with the controlled vocabulary like keyword-extract's, extract capture context, label text, object count, a vocabulary-based description and labelled object segments from archive images?

This plan authorises no production model, API, label-registry, schema or release change.

## Context

The classifier has a mature, image-only baseline: 11 labels whose `model_registry.CATEGORIES` order is bound to the checkpoints. Its only held-out figures are per fold. Each `vX.4` model was scored on the test partition of the fold it trained on, and the ensemble has none (`docs/evaluation/results.md`).

Cloudflare's Clef family answers typed decisions over a choice schema, with per-option probabilities, which suits track 1 and track 2's closed questions. Track 2's description, label text and segments need a generative, grounding VLM. Public benchmarks predict neither.

**Runtime:** this repository pins PyTorch 2.7.1 and `transformers<5`; the Clef card was tested with 2.11 and 5.10.2. Every candidate runs in its own environment.

## Track 1: LDMs on the page categories

### Phase A: freeze inputs, prove the runtime

1. Record: the tested commit, model ids and exact revisions, card dates, dtype or quantisation, inference framework and versions, GPU and memory, Slurm resources.
2. Build a separate environment or container. Do not touch `setup/requirements.txt`, the production image or the registry. Start with `clef-flash`.
3. Run a smoke set of 3–5 pages per label, from the fold-1 **training** partition, not its test pages. Verify: image input, typed output, probability extraction, error handling, the link from each answer to its file, and resume.
4. Measure cold load apart from steady-state latency, and peak RAM/VRAM. Hosted inference is a separate option that needs a data-governance check first.

### Phase B: define the two classification tasks

**B1. The 11 labels (control).** `DRAW`, `DRAW_L`, `LINE_HW`, `LINE_P`, `LINE_T`, `PHOTO`, `PHOTO_L`, `TEXT`, `TEXT_HW`, `TEXT_P`, `TEXT_T`. Use one typed `choice` question with criteria taken from `docs/reference/categories.md`, zero-shot. Save every label's probability, the prediction, the status and the prompt version. The ids always map to these names; `CATEGORIES` is never reordered.

**B2. Processor-aware extension.** Agree a table with the downstream owners before running:

| Field                    | Required definition                                                  |
|--------------------------|----------------------------------------------------------------------|
| Extended label or route  | Stable id and short name                                             |
| Meaning                  | Observable properties and decision rule, with borderline cases       |
| Target processor         | Existing or explicitly planned processor                             |
| Mapping to the 11 labels | One-to-one, one-to-many, or not derivable, with the reason           |
| Evidence / gold          | Existing annotation, a rule approved in advance, or new adjudication |
| Frequency                | Eligible examples and whether the class is represented enough        |

- **The first row is now concrete:** route `image_description` → the track-2 describer, for `PHOTO`, `PHOTO_L`, `DRAW` and `DRAW_L`.
- **Other candidate routes** are proposals until checked against each processor's real capabilities: typed/printed OCR, handwriting, table-aware extraction, manual review.
- Keep `page_category` (one of the 11) separate from `processing_route` where a route is not a content class.

### Phase C: fix the evaluation set and baselines

1. **Use the fold-1 test partition** (4,795 pages, from the [LINDAT record](http://hdl.handle.net/20.500.12800/1-6184) split). It is held out for both `v1.4` and `v4.4`. Record its manifest and checksum.
2. **Do not use the 5,449-page set.** Most of its pages are training pages (`docs/evaluation/results.md`).
3. **Baselines:** rerun `v1.4` and `v4.4` on exactly these files and capture the loaded revisions. The `--best` ensemble may be run for context, labelled as having no held-out figure. `v2.4`, `v3.4` and `v5.4` are not held out on fold 1.
4. **Report the unseen-document subset separately.** About a quarter of the test pages come from documents with other pages in training; results.md gives 95.60 / 95.19 % for that subset.
5. **No leakage:** no test pages as few-shot examples; no rewording after looking at test errors; criteria developed on the fold-1 dev partition.

### Phase D: run the decision models

Run them in order: `clef-flash`, then `clef` if the trade-off warrants it, then `clef-omni` if its card and runtime support image input locally. Use one fixed zero-shot schema. At most one predeclared ablation (concise vs full criteria) on dev, frozen before test. Use the typed decision interface only.

### Phase E: evaluate

- Top-1, balanced accuracy, macro-F1, per-class P/R/F1, and the confusion matrix. Pay particular attention to `TEXT_T`/`TEXT` and `LINE_HW`/`LINE_T`, the known weak pairs.
- An exact McNemar test against `v1.4` and `v4.4` on the same pages. Differences inside ±0.6 points are not claimed.
- Calibration (Brier, ECE) and coverage against error for a manual-review threshold. Compare with the baseline's top-3 fallback (99.75–99.90 %).
- Cold start, median/p95 latency, pages per second, peak memory, and failures, timeouts and retries (never dropped).
- Per-document breakdown where ids exist.

## Track 2: structured description of archive images

### Phase F: output schema and prompt

1. **Schema (experiment JSON, not a record block):**

   ```json
   {
     "capture_context": "dig | post_dig_lab | other | unknown",
     "capture_context_confidence": 0.0,
     "labels": [{"text": "…", "kv": {"key": "value"}, "bbox": [0, 0, 0, 0]}],
     "object_count_pattern": "1 | N | 1a..1n",
     "object_count": 0,
     "description": "…",
     "terms": [{"term": "…", "facet": "Artefact", "uri": "…"}],
     "objects": [{"term": "…", "instance": "1a", "bbox": [0, 0, 0, 0]}]
   }
   ```

   `1` = one instance of one object; `N` = one instance each of several objects; `1a…1n` = several instances or views of one object (`objects[].instance` carries the letter).
2. **Prompt:** a `system_prompt.txt`-style block file loaded with keyword-extract's `prompt_template.py` format, with flags for optional blocks.
   - Role, then the task, then the rules: JSON only, terms only from the list, `unknown` allowed.
   - The vocabulary is injected after its header from `data_samples/vocab/union_nested.json`, restricted to the facets that describe objects: Artefact, Material, Feature, Finds Context, Chronology.
   - Plus the new `capture_context` list with definitions, and an output template like `prompts/output_template.json`.
   - Vendor or pin the prompt module rather than importing keyword-extract's tree.
3. **Inputs:** one or more images of the same item. The linked document's description and text are an optional block, switched by a flag.
4. **Closed fields by an LDM:** `capture_context` and `object_count_pattern` can also be asked as Clef typed decisions. Compare them with the VLM's answers to the same questions.

### Phase G: gold set

- Select pages predicted `PHOTO`, `PHOTO_L`, `DRAW` or `DRAW_L` from the dev/test partitions. Draw a stratified sample across sources and categories, sized by annotation capacity (start at ~100–200 images).
- Annotators (ARÚP/ARÚB): `capture_context`, label text (+ KV), object count pattern and count, object boxes with vocabulary terms. Keep a written rule sheet and measure agreement on a double-annotated batch.
- Never use model output as gold. Record the annotation tool, the guidelines version and the checksum.

### Phase H: runs and metrics

- **Runs:** with and without the linked document (the leakage check), per model, pinned.
- **Metrics:**
  - `capture_context` and `object_count_pattern`: accuracy, macro-F1, confusion matrix;
  - `object_count`: exact match and absolute error;
  - labels: CER/WER (atrium-project#22's `eval_metrics` can be reused), plus KV field F1;
  - terms: precision/recall against the gold terms;
  - `objects`: IoU-matched precision/recall per term, and mAP where scores exist;
  - operational figures as in Phase E.
- **Invalid JSON** is counted as a failure, not repaired silently.

### Phase I: hardware sizing

- **Spark-class unit:** 128 GB unified memory (two can be linked), ~273 GB/s memory bandwidth. _Check against NVIDIA's current specification._ Budget weights ≤ ~100 GB per unit, leaving room for the KV cache and image tokens.
- **Shortlist to verify at run time** (weights ≈ parameters × bytes per parameter): Clef-Flash 9B (~18 GB, bf16), Clef 27B (~54 GB), Llama 4 Scout 109B MoE (FP8 ~110 GB), GLM-4.5V 106B MoE (FP8 ~106 GB), Qwen3-VL-235B-A22B (4-bit ~120 GB+, two units or tight), InternVL3.5-241B-A28B (4-bit ~125 GB+, two units).
- **Larger models** (e.g. MiniMax-M3-MXFP8) go to the Grace Hopper machine via Viktor, as stranak noted on atrium-project#22 (06-19).
- **Per model, record:** whether it loads, the quantisation and its quality cost (a small dev comparison against a higher precision where it fits), the time per image, and memory headroom.

## Phase J: record the outcome

Write one report under an issue-specific experiment directory or `agent_dev_logs/` with:
- commands or a runnable script, the prompt and schema text, pinned revisions;
- the split manifest and the gold checksum;
- metric definitions, resources, full results and error cases.

Conclude per track:
- **Stop:** no gain, or the model is not reproducible on the hardware available.
- **Keep as a research option:** useful for a narrow class, a route or a field.
- **Propose a follow-up:** for example, a record block for image descriptions and segments (atrium-project#71, shared with #22's region check), or a service integration, each as its own reviewed task.

## Done criteria

- [ ] The track-1 task definitions and the extended mapping are recorded and justified by processor needs.
- [ ] A pinned smoke test proves each candidate ingests the real images and returns usable typed or JSON output.
- [ ] At least one LDM is scored on the fold-1 test partition against `v1.4` and `v4.4`, with the unseen-document subset reported and every failure recorded.
- [ ] The track-2 schema, prompt and `capture_context` list are written and reviewed with a domain annotator.
- [ ] A track-2 gold set exists, or its absence is documented as the blocker.
- [ ] Track-2 fields are scored with and without the linked document.
- [ ] At least one Spark-class-sized model has been sized and tried, or ruled out with a reason.
- [ ] Results and limits are reproducible from the recorded artefacts; nothing in production changed.

## Out of scope

- Reordering or changing `model_registry.CATEGORIES`, or relabelling checkpoints.
- LDM or VLM inference in the production API, or a change to the classifier default.
- A record schema change for descriptions or segments (propose under atrium-project#71 if the evidence supports it).
- Fine-tuning before a zero-shot result justifies it.
- A large re-annotation campaign before the small gold set shows the fields are useful.
- Sending archival images to hosted inference without approval.

## Refresh conditions

Refresh after any of these:
- the first smoke run;
- agreement on the extended routes or the track-2 schema;
- the first gold batch;
- the first comparable results;
- a hardware decision.

Before every new sweep, re-check the candidate cards.
