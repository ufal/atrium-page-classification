## Context

The classifier has a mature, image-only baseline: 11 labels whose `model_registry.CATEGORIES` order is bound to the
checkpoints. Its only held-out figures are per fold. Each `vX.4` model was scored on the test partition of the fold it
trained on, and the ensemble has none (`docs/evaluation/results.md`).

**What a decision model is.** It reads a *state* (text or JSON, plus images) and a set of typed questions in one
prefill pass. It returns a probability for every allowed option and generates no text.
- Question types:
  - `choice`: 2–255 options; `criteria` maps each option id to a description, or to null.
  - `noul`: yes or no.
  - `score`: an ordered list.
- A `choice` answer carries `choice`, `probabilities` and `confidence`; a `noul` answer carries P(true).
- A request holds at most 64 questions and 4 images.
- The output cannot leave the schema, but it can still pick the wrong option.

## Phase 0: the shared client and the servers

**The client: `decision_client.py`**, at this repository's root.
- **Dependencies:** the standard library only (`urllib`), so no consumer gains a dependency. Pillow is imported lazily,
  for images only. No torch.
- **Builders:** `choice()`, `noul()` and `score()`. They check: 2–255 options, at most 64 questions, at most 4
  images, unique ids.
- **`image_data_uri(img, max_side=1024)`:** resizes and encodes as JPEG. A large scan otherwise fills the context.
- **`DecisionClient(url, model, timeout_s, retries).decide(state, questions, images)`:** returns a `Decision`.
  - **It never raises.** Statuses: `ok`, `invalid`, `timeout`, `error`, `rejected`, `not_configured`. The status set
    follows digital-convert's stage connector (`service/stages.py:_post`).
  - Each call records its latency and `usage.input_tokens`.
- **Strict validation:** a choice outside the options, or probabilities that do not cover them or do not sum to about
  1, gives `invalid`. It is counted, never repaired.
- **`lane(answer, accept_at, review_below)`:** returns `accept`, `escalate` or `review`. The thresholds are set on dev
  data, per model and per question wording; they do not transfer.
- **`schema_digest(questions)`:** the SHA-256 of the canonical JSON of a question set. It serves as the prompt
  version.
- **Metrics, shared so the four repositories report alike:** Brier, ECE (10 bins), coverage against error,
  `pick_threshold(target_error)` and an exact McNemar.
- **`--selftest`:** runs against an in-process fake `/v1/systemone`, the way the hub's selftests run.
- **`--probe`:** four checks of a live server:
  1. the card's two requests;
  2. one image question in each of the four image forms (`IMAGE_STYLES`: a `data:` URI, bare base64, `{"url": …}`,
     the OpenAI-style `image_url`), and once without an image;
  3. a request at the limits (a 255-option choice and 63 yes/no questions).

  The report names the endpoint `$DECISION_MODEL_URL`, never the host.
- **Written 11-06 (evening), not pushed.** It follows the wire format of the Clef card's
  `joint_schema_model.systemone`:
  - questions are keyed by id;
  - a `noul` answer is `{"type": "noul", "noul": p}`;
  - probabilities are rounded to 4 decimals, which the sum check allows for;
  - `usage.input_tokens` is reported.
  - It is tested by `tests/test_decision_client.py` (56 tests) and the selftest's 15 cases. `FakeSystemOne` and
    `reference_answers()` answer in the card's shapes, for the consumers' tests too.
  - The defaults `DECISION_*` are declared under `NOT_PUBLISHED` in `tests/env_contract_data.py`.

**Question sets** are versioned JSON (`decisions/<name>.v<N>.json`). Their criteria text is generated from the
vendored `atrium_vocab` (`CONCEPTS['page-category']`, built from `_PAGE_CATEGORY_DEFS`), so the definitions exist
once. Written 11-06: `decide_pages.py --write-question-sets` writes `decisions/page_category.v1.json` (digest
`c38813ff…`) and `decisions/page_routes.v1.json`; a test fails when they drift.

**Copies.**

  `tests/test_vendored_decision_parity.py` (`VENDORED` SHA-256 plus `ADOPTED`), the way `text_formats.py` and

### Phase B: the tasks (B1, B2, B3, B4; triage = B3 + B4)

**All four decide form, from the image alone** (atrium-project#83, "Form and content"): the page's layout and script
(B1, B2), what kinds of marks are on it and which processors it needs (B3), its physical condition and orientation
(B4). None asks what the page is about. In B4, "content" names the marks on the paper (ink, print, pictures) as
against the paper itself, not the document's subject.

Experiment CLI `decide_pages.py`, outside `service/`. It runs in the repository's own environment: the model is on
the server, so no torch is loaded and no `requirements_decide.txt` is needed (written 11-06, not pushed;
`tests/test_decide_pages.py`, 16 tests).
- **As written:**
  - B2 reads a `run.py --raw` table and sends only the pages below τ, with the CNN's top 3.
  - `CLASS-1` is the cascade's answer for every page. A failed decision keeps the CNN's.
  - `--resume --out` continues a run.
  - A `.summary.json` and a paradata record (`decision_model` in `setup/para_config.txt`) sit beside the table.
- Inputs: images or a folds CSV.
- Output, `DECIDE_RAW.csv`: `FILE`, `PAGE`, one column per option probability, `choice`, `confidence`, `lane`,
  `status`, `latency_ms`, `schema_digest`. `utils.confusion_plot` and `data_scripts/eval_by_document_overlap.py` read it
  as they read `TOP-N_EVAL`.

**B1. The 11 labels, standalone (control).** `DRAW`, `DRAW_L`, `LINE_HW`, `LINE_P`, `LINE_T`, `PHOTO`, `PHOTO_L`,
`TEXT`, `TEXT_HW`, `TEXT_P`, `TEXT_T`.
- One typed `choice`, zero-shot. Criteria come from `docs/reference/categories.md`.
- The ids always map to these names; `CATEGORIES` is never reordered.

**B2. The cascade (the shape that could ship).**
- The CNN answers every page. When its top-1 probability is below τ, the LDM chooses among the CNN's top 3 labels
  only.
  - The probability is taken from the **raw** table (`--raw`, the full softmax). It is not taken from `SCORE-1`,
    which `classifier.topn_pairs` renormalises over the best classes.
  - Top-3 holds the true label on 99.90 % (`v1.4`) and 99.79 % (`v4.4`) of the fold-1 test pages.
- Report:
  - how many pages are deferred;
  - on the deferred pages, those the LDM fixes against those it breaks;
  - the net top-1;
  - the time per deferred page.
- τ is set on dev, from the coverage-against-error curve.
- **Why this shape:** the CNN is already at ~96 % and cheaper. The LDM is worth its cost only where the CNN is unsure.

**B3. Page triage: elements and processors** (rewritten 2026-11-08; `decisions/page_routes.v2.json`, digest
`35330a46…`). The goal is a tag per further processor, for triage of incoming pages. A page can carry everything at
once (a table, a drawing, a photograph and a stamp with filled-in fields), so the processors are not one `choice`.
- **Seven `noul` elements**, what can be seen on the page: `has_printed_text`, `has_handwriting`, `has_table_form`,
  `has_filled_fields`, `has_photo`, `has_drawing` (drawings, maps, plans, sections), `has_stamp`.
- **Four processor tags, computed in code** (`ROUTE_ELEMENTS`). P(tag) is the largest P of its elements.

  | Tag        | Processor                              | From the elements                      |
  |------------|----------------------------------------|----------------------------------------|
  | `ocr`      | printed or typed text recognition      | printed text                           |
  | `htr`      | handwritten text recognition           | handwriting                            |
  | `tables`   | table and form structured extraction   | table or form, filled-in fields, stamp |
  | `graphics` | photo and drawing detection/extraction | photograph, drawing                    |

  A stamp goes with tables and forms: an archive stamp is a small form with filled-in fields.
- **One `choice`, `primary_route`:** the processor that matters most, for a single triage label.
- **Gold, at no cost, from the true label:**
  - **Elements are three-state.** Present: the hub vocabulary's `COLLECTIONS['page-category']` (printed ∪ typed,
    handwritten, tabular; the PHOTO and DRAW members of graphical). Absent: only the "only …" labels (`TEXT_HW`,
    `TEXT_P`, `TEXT_T`). Unknown otherwise. Filled-in fields and stamps have no gold until annotated.
  - **Tags** follow the hub's next-step table (`docs_site/workflows/page-classification.md`), as v1's routes did.
  - **Primary** is an accept set: `TEXT` → ocr or htr; `DRAW_L`/`PHOTO_L` → graphics or tables.
- **Reported:** per element and tag, P/R/F1 on known gold (no precision without known negatives); exact tag-set
  match; primary accuracy.
- v1's four routes (`page_routes.v1.json`) were never run and are removed. `route_image_description` becomes
  `graphics`.

**B4. Page condition** (new 2026-11-08; `decisions/page_condition.v1.json`, digest `6840075b…`). How damaged is the
page, as paper and as content?
- **Fifteen `noul` defects, in three aspects:**
  - paper: `stained`, `yellowed`, `torn_edges`, `water_damage`, `folds_creases`, `holes_missing`, `foxing_mould`;
  - content: `faint_ink`, `bleed_through`, `smudged_ink`;
  - capture: `skewed`, `rotated_text`, `blurred`, `cropped`, `uneven_light`.
- **`orientation`** (`choice`): upright, a quarter clockwise, upside down, a quarter counter-clockwise, or unclear.
- **Three `score` questions**, 0 (none) to 4 (severe): `paper_condition`, `content_condition`, `overall_damage`.
  `damage_score` = `overall_damage` / 4 is the headline figure.
- **Check indices, computed in code:** the equal-weight mean of the defect P per aspect (`paper_index`,
  `content_index`, `capture_index`) and over all (`damage_index`). They are compared with the model's own scores
  (Spearman), never used in their place.
- **`--task triage`** sends B3 and B4 together: 27 questions, one prefill of the image.

**Phase S: synthetic gold for B4** (`data_scripts/degrade_pages.py`, new 2026-11-08). No page of the dataset is
labelled for its condition.
- Seven defects can be made with a filter on clean pages, at three levels:
  - `skewed` (2/4/8°), `yellowed` (tint), `faint_ink` (fade to the paper's colour), `blurred`;
  - `cropped` (8/15/25 % of one side), `uneven_light` (a shadow gradient);
  - `rotated_text` (three turns; the gold of `orientation`).
- **Output:** the original and its copies in the `<LABEL>/` layout, and a manifest. `decide_pages.py --degradations`
  reads the manifest, so each copy pairs with its original.
- **Reported per injected defect:** the paired change of its P (degraded − original), the detection rate, the false
  alarms on the originals. Also orientation accuracy on text pages, and Spearman(level, `overall_damage`).
- **Not faked:** stains, tears, water damage, folds, holes, foxing, bleed-through, smudges, and the three scores on
  real pages. They need annotated pages: question 4 of atrium-project#83, widened to a defect checklist.
- **Inputs:** the public `small_data_samples` and fold-1 training pages first; the dev partition for thresholds.

## Track 2: structured description of archive images

### Phase F: output schema and prompt (image only since 2026-11-09)

**What Track 2 may decide.** This repository sees images only, so it decides form, and from content only what can
be seen in the picture (atrium-project#83, "Form and content"):
- **form:** the picture's AMČR type (a photograph of a site, of a feature, of an object …; a plan; a map; an object
  drawing) and its object count;
- **depicted objects:** terms from the vocabulary's visual facets, Artefact, Material and Feature, for what is shown;
- **not:** dating, culture, the find's context, the site or place, or anything else that is read rather than seen.
  Those are content, and content comes from text: a picture's label text, transcribed here, goes on as text to
  keyword-extract like any OCR line.

1. **Schema (experiment JSON, not a record block):**

   ```json
   {
     "image_type": "photo_object | photo_feature | photo_excavation | … | object_drawing | map | unspecified",
     "image_type_confidence": 0.0,
     "labels": [{"text": "…", "bbox": [0, 0, 0, 0]}],
     "object_count_pattern": "1 | N | 1a..1n",
     "object_count": 0,
     "description": "…",
     "terms": [{"term": "…", "facet": "Artefact | Material | Feature", "uri": "…"}],
     "objects": [{"term": "…", "instance": "1a", "bbox": [0, 0, 0, 0]}]
   }
   ```

   - `image_type` is AMČR's `dokument_typ` picture type, the options of digital-convert's
     `decisions/document_type.v3.json` view `pdf_page` (`image_type`: 25 picture types and `unspecified`). It
     replaces 11-05's `capture_context`: dig against lab is what AMČR's own types tell apart (`photo_excavation`,
     `photo_feature`, `photo_site` against `photo_object`, `microphotograph`, `photo_conservation`), so the archive's
     terms are used and no new list is made. The list is vendored from digital-convert when Track 2 is written, which
     needs a digital-convert release with v3 and a row in the hub's `docs/shared_components.md`.
   - `labels` are transcribed text with their boxes, nothing more: parsing them into keys and values is reading,
     which is the text tools' job.
   - `description` says what is visible, without dating or interpretation.
   - `1` = one instance of one object; `N` = one instance each of several objects; `1a…1n` = several instances or
     views of one object (`objects[].instance` carries the letter).
2. **Prompt:** a `system_prompt.txt`-style block file loaded with keyword-extract's `prompt_template.py` format, with
   flags for optional blocks.
   - Role, then the task, then the rules: JSON only, terms only from the list, `unknown` allowed, nothing that is
     not visible.
   - The vocabulary is injected after its header from `data_samples/vocab/union_nested.json`, restricted to the
     visual facets: Artefact, Material, Feature. Chronology and Finds Context are not offered: an image does not show
     them.
   - Plus the picture types with their definitions, and an output template like `prompts/output_template.json`.
   - Vendor or pin the prompt module rather than importing keyword-extract's tree.
3. **Inputs:** one or more images of the same item (a decision request takes at most four). No text: not the linked
   document's description, not its OCR.
4. **Closed fields by an LDM:** `image_type` (`choice`, the `pdf_page` view's question) and `object_count_pattern`
   (`choice`) are also asked as decision questions through the Phase 0 client. Compare them with the VLM's answers
   to the same questions, and `image_type` with digital-convert's answers where the same item is a PDF page.

### Phase G: gold set

- Select pages predicted `PHOTO`, `PHOTO_L`, `DRAW` or `DRAW_L` from the dev/test partitions. Draw a stratified
  sample across sources and categories, sized by annotation capacity (start at ~100–200 images).
- Annotators (ARÚP/ARÚB), looking at the image only: the AMČR picture type, label text, object count pattern and
  count, object boxes with visual-facet terms. Keep a written rule sheet and measure agreement on a double-annotated
  batch.
- Never use model output as gold. Record the annotation tool, the guidelines version and the checksum.

### Phase H: runs and metrics

- **Runs:** images only, per model, pinned. (The with/without-document runs of 11-05 are dropped with the text
  input.)
- **Metrics:**
  - `image_type` and `object_count_pattern`: accuracy, macro-F1, confusion matrix, and calibration for the LDM
    answers;
  - `object_count`: exact match and absolute error;
  - labels: CER/WER (atrium-project#22's `eval_metrics` can be reused);
  - terms: precision/recall against the gold terms;
  - `objects`: IoU-matched precision/recall per term, and mAP where scores exist;
  - operational figures as in Phase E.
- **Invalid JSON** is counted as a failure, not repaired silently.

### Phase I: hardware sizing

- **Spark-class unit:** 128 GB unified memory (two can be linked), ~273 GB/s memory bandwidth. _Check against
  NVIDIA's current specification._ Budget weights ≤ ~100 GB per unit, leaving room for the KV cache and image tokens.
- **The three decision models are small:**
  - Clef ~54 GB in bf16 (the card ran on one H200);
  - Clef-Flash ~18 GB;
  - Strands ~4 GB, which runs on a CPU.
  - A decision model only prefills, so it needs no sampling setup.
- **Track-2 VLM shortlist, to verify at run time** (weights ≈ parameters × bytes per parameter): Llama 4 Scout 109B
  MoE (FP8 ~110 GB), GLM-4.5V 106B MoE (FP8 ~106 GB), Qwen3-VL-235B-A22B (4-bit ~120 GB+, two units or tight),
  InternVL3.5-241B-A28B (4-bit ~125 GB+, two units).
- **The internal endpoint (11-06)** is a Mac-class machine. It serves the 8-bit Clef beside a generative model
  (`Qwen3.8-Flash-Next-oQ8e-mtp`). Its throughput under that shared load is measured in Phase A, not assumed.
- **Larger models** (e.g. MiniMax-M3-MXFP8) go to the Grace Hopper machine via Viktor, as stranak noted on
  atrium-project#22 (06-19).
- **Per model, record:**
  - whether it loads;
  - the quantisation and its quality cost (a small dev comparison against a higher precision where it fits);
  - the time per image;
  - the memory headroom.

## Out of scope

- Reordering or changing `model_registry.CATEGORIES`, or relabelling checkpoints.

- A record schema change for routes, descriptions, segments or document types (propose under atrium-project#71 if
