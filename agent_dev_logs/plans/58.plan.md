# Strategy — Issue [#58](https://github.com/ufal/atrium-page-classification/issues/58): Experiment with LDMs (Large Decision Models) with current and extended categories

> _Drafted 2026-10-20 against `test` at `0f9ae3ecc049`; no issue comments or experiment outputs exist yet. Summary: [`../digests/58.digest.md`](../digests/58.digest.md)._

**Status**: 🧪 **New exploratory task — experiment design and feasibility first.** The goal is to learn whether recent decision models can classify historical page images at useful accuracy, speed and cost, both on the existing 11 labels and on an extended set that reflects downstream processing. This plan does not authorise a production model, API, label-registry or release change.

## Context

The current classifier has a mature, evaluated image-only baseline. It emits one of 11 structural labels; the canonical `CATEGORIES` order in `model_registry.py` is bound to existing checkpoints and must not change. The production ensemble uses the `v*.4` revisions, while `v4.4` (`regnety_160`) provides a useful single-model comparator.

Cloudflare's Clef family is relevant because it answers typed decisions over an explicit choice schema and exposes per-option probabilities. The currently published cards cover image input; Clef-omni is an additional multimodal option. These capabilities make the family suitable for a controlled zero-shot trial, but public general-purpose benchmarks cannot predict performance on archive images. The actual task benchmark must decide whether it is useful.

Repository/runtime caution: the standard page-classification setup pins PyTorch 2.7.1 and `transformers<5`, while the current Clef card documents testing with PyTorch 2.11 and `transformers` 5.10.2 on an H200. Keep candidate-model dependencies isolated from the production application until compatibility and resource use are understood.

## Experimental protocol

### Phase A — Freeze the inputs and prove the runtime

1. Record the tested `test` commit, candidate model IDs and exact Hugging Face revisions / commit hashes, model-card date, dtype / quantisation, inference framework, dependency versions, GPU type and memory, Slurm resources, and relevant environment settings. Re-check cards before launch because model releases and runtime support are moving quickly.
2. Create a separate experiment environment or container. Do **not** change `setup/requirements.txt`, the production image, or model-registry mappings to make the LDM load. First test `clef-flash` as the smallest candidate; only proceed to the 27B Clef and the 30B-MoE / 3B-active Clef-omni if the local allocation can support them.
3. Run a small stratified smoke set across all 11 current labels (for example, 3–5 examples per label where available). Verify real image input, schema-constrained output, probability extraction, unknown/error handling, deterministic record association and successful retry/resume behaviour. Save per-example outputs without changing original files.
4. Measure cold model-load time separately from steady-state latency; record RAM/VRAM peaks and any model download/cache requirement. If local inference is infeasible, treat hosted inference as a separate option requiring an explicit data-governance check before any real archival material is uploaded.

### Phase B — Define the two classification tasks

**B1. Existing taxonomy (control condition).** Use the exact 11 stable labels:

`DRAW`, `DRAW_L`, `LINE_HW`, `LINE_P`, `LINE_T`, `PHOTO`, `PHOTO_L`, `TEXT`, `TEXT_HW`, `TEXT_P`, `TEXT_T`.

The display order in the request need not equal checkpoint order, but label IDs must always map to the names above; never reorder or rewrite `model_registry.CATEGORIES`. Use one typed `choice` question with concise criteria copied from / aligned with the repository's category definitions. Begin zero-shot, without examples from the evaluation set. Save every label's probability, predicted label, run status and prompt/schema version.

**B2. Extended processing-aware task.** Before running it, build and review a table with the downstream tool owners:

| Field                            | Required definition                                                              |
|----------------------------------|----------------------------------------------------------------------------------|
| Extended label or route          | Stable ID and short name for the added distinction or next action                |
| Meaning                          | Observable page properties / decision rule, including borderline cases           |
| Target processor                 | Existing or explicitly planned processor that would act on the page              |
| Mapping to the 11 labels         | One-to-one, one-to-many, or not derivable; record the rationale                  |
| Evidence / gold label            | Existing annotation, derived rule approved in advance, or new human adjudication |
| Frequency and evaluation support | Number of eligible examples and whether the class is sufficiently represented    |

Prefer a structured / hierarchical output that keeps `page_category` (one of the original 11) separate from a new `processing_route` field when the route is not equivalent to a content class. Candidate routes could include printed/typed-text OCR, handwriting recognition, table-aware extraction, drawing/map processing, photo handling, and manual review/no-op, but these are **proposals to validate against actual processor capabilities**, not approved labels. If an extended flat label set is required, define its exhaustive and mutually exclusive mapping first. Do not silently force a single route where several downstream actions are valid.

Do not invent gold labels by taking the LDM or current classifier's predictions as truth. If the existing annotations cannot provide the proposed extension, select a small, documented subset for independent annotation/adjudication, keep the annotators' rules and disagreements, and report the reduced sample size as a limitation.

### Phase C — Fix the evaluation set and baselines

1. Identify the canonical held-out split in the staged cluster data and record its source dataset revision, fold/split manifest, random seed, and any exclusions. The paper has described a 5,449-page test set; verify that this is the actual intended split before using that count. Do not use a training/dev sample as a replacement test set and do not change evaluation membership between model runs.
2. Avoid test leakage: do not add test examples to the prompt as few-shot demonstrations, tune category wording after examining individual test errors, or use the test split to settle the extended taxonomy. Develop the category definitions on repository docs and a separate development sample first.
3. Run current baselines against the exact same image files and gold labels: (a) production `--best` / the five `v*.4` ensemble and (b) `v4.4` as a single model. Capture the checkpoint/model revisions actually loaded. A baseline that fails to load fully must be recorded as partial, not silently compared as the full ensemble.
4. Keep original images, pre-processing, label normalisation and evaluation code the same wherever possible. If an LDM has a different mandatory image resizing path, record that difference and avoid unnecessary preprocessing variants in the first pass.

### Phase D — Compare the decision models

Run sequentially, not as a broad blind sweep:

1. `Cloudflare/clef-flash` for the initial small-sample feasibility and first full run if feasible.
2. `Cloudflare/clef` on the same inputs if the accuracy/resource trade-off warrants the larger model.
3. `Cloudflare/clef-omni` if the current model card, local weights and available runtime support image input reliably. Its 30B MoE backbone / 3B active parameters make it a distinct runtime candidate rather than a presumed drop-in equivalent.

For each model, begin with one fixed zero-shot schema and documented criteria. At most add a small, predeclared prompt/schema ablation (e.g., concise versus fuller criteria) on the development set; freeze the winning configuration before final test evaluation. Use the models' typed choice outputs and per-option probabilities, not free-form text that needs heuristic parsing. Pin the exact model revision and use the documented decision-model interface; do not assume a generic chat-completion request exposes the joint decision head correctly.

### Phase E — Evaluate both tasks

For the existing 11-label task, and separately for any gold-labelled extended task, record:

- top-1 accuracy and balanced accuracy;
- macro-F1 and per-class precision / recall / F1;
- confusion matrix and representative error examples, especially confusions that would send a page to the wrong processor;
- per-option confidence, calibration (Brier score / ECE where sample size permits), and coverage-versus-error if a low-confidence/manual-review threshold is useful;
- cold start separately from steady-state median / p95 latency, pages per second, peak RAM / VRAM, errors/timeouts/retries, and input-token or hosted inference cost where applicable;
- performance by source PDF/document if document IDs are available, to expose clusters of similar pages and avoid overclaiming generalisation from near-duplicate pages.

Report sample counts for each class and every failure/omission. Do not drop timeouts, invalid responses or memory failures from the operational comparison. Public benchmark scores are context only; they are not a substitute for these task-specific results.

### Phase F — Record the outcome

Write a concise result report under an issue-specific experiment directory or in `agent_dev_logs` (use the existing repo convention and link any generated table/CSV). Include exact commands or a runnable script, prompt/schema text, pinned revisions, split manifest, metric definitions, resource measurements, full results and error cases.

Conclude one of three ways:

- **Stop:** current classifiers are clearly preferable or the candidate models cannot be run reproducibly on the available infrastructure.
- **Keep as a research option:** the LDM is promising for a narrow class or routing decision, but not ready to displace the current classifier.
- **Propose a separate follow-up:** strong evidence supports a broader experiment or service integration. Any production change, taxonomy update, model default change or API contract change gets its own reviewed task.

## Done criteria

- [ ] Current and extended task definitions are recorded, and the exact extended mapping is justified by downstream processing needs.
- [ ] A pinned, reproducible smoke test proves the model can ingest the actual page images and return usable typed scores in the chosen environment.
- [ ] At least one candidate LDM is evaluated against the 11-label task on the same frozen, gold-labelled split as the conventional baselines; all outcomes, including failures, are recorded.
- [ ] If gold labels for the extension exist or are created, the processing-aware task receives a separate, honest evaluation; otherwise the missing-label requirement and blocker are documented.
- [ ] The production `--best` ensemble and `v4.4` single-model baseline are rerun against the same test subset, with exact revisions and any partial-model failures visible.
- [ ] Metrics cover predictive quality and operational efficiency (latency, resource use, and cost where applicable), with class-level error analysis.
- [ ] Results and limitations are written down with enough detail to reproduce them; no production taxonomy, registry, API, default, or release is changed by this exploratory issue alone.

## Out of scope

- Changing the order or membership of `model_registry.CATEGORIES` or relabelling existing checkpoints.
- Shipping LDM inference in the production API or switching the production classifier default.
- Fine-tuning / reinforcement-learning adaptation of the decision models before a zero-shot baseline justifies the additional work.
- A large-scale manual re-annotation campaign without first proving that the extended routing distinctions are useful.
- Sending archival images to hosted inference without the necessary rights / data-governance approval.

## Refresh conditions

Refresh this plan after the feasibility run, when the downstream owners agree on the extended labels, when the held-out split is identified, or when the first comparable baseline/LDM results exist. Update candidate versions from pinned model cards before any new sweep.
