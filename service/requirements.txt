# service/requirements.txt — RUNTIME manifest for the FastAPI service.
#
# This file used to hold six pytest/contract deps and no ASGI server at all
# (atrium-project#10, G3). Nothing noticed for 12 days, because nothing runs the image it
# builds: tests/test_service_api.py and tests/test_api_contract.py drive the app in-process
# through TestClient — which needs no server — and the hub's docker-build-smoke job only
# BUILDS the image. Meanwhile docker-compose.yml's `api` service entrypoint is
# `uvicorn service.api:app` and setup/setup_api_service.sh tells the user the same, so
# `docker compose --profile api up api` died at container start with "executable file not
# found". tests/test_service_runtime_deps.py is the gate: it parses the compose file and
# the setup script for the console entrypoints they invoke and asserts each one is declared
# in an installed requirements file, so pruning this list reddens the fast lane instead of
# only the deployment.
#
# Test deps are NOT duplicated here — they live in setup/requirements-test.txt (which the
# root requirements-test.txt forwards to, and which the Docker image and CI both install).
#
# The model stack (torch/transformers/timm/pandas/…) is deliberately NOT pulled in with a
# `-r ../setup/requirements.txt`: the Dockerfile flattens this file to /app/service-
# requirements.txt (Dockerfile:41), so a relative include would resolve to a path that does
# not exist in the image. Both are installed side by side there and by
# setup/setup_api_service.sh, so keep this list additive and flat.
# fastapi and pydantic are pinned EXACTLY (atrium-project#32 round 2): the committed
# service/openapi.json — the spec every release attaches, and AMČR generates its clients
# from — is a function of both, and tests/test_openapi_contract.py fails when the installed
# versions differ from these pins. Bump them together by hand, in setup/requirements-test.txt
# too, and regenerate the spec in the same commit (python atrium_openapi.py export --app
# service.api:app --prepare tests.openapi_contract_data:prepare); dependabot ignores both.
fastapi==0.141.1
uvicorn[standard]>=0.54.0
python-multipart>=0.0.32
# api.py builds its response models with pydantic directly, so it is declared directly rather
# than relied on as fastapi's transitive dependency.
pydantic==2.13.5
# service/api.py: `Image.open(...)` on every /predict_image request.
Pillow>=12.3.0
# service/api.py's /predict_document rasterises PDF pages with pypdfium2 (Apache-2.0 /
# BSD-3-Clause; the PDFium it bundles is BSD-3-Clause), declared in setup/para_config.txt.
# It replaced PyMuPDF (AGPL-3.0), which was imported here, installed in both published images
# and declared nowhere, so a /predict_document record left it out of its derived licence
# (atrium-project#6 D, #72 D.1; the engine comparison is data_scripts/pdf_rasteriser_comparison.md).
# Same range as atrium-alto-postprocess, which reads PDF text layers with it. PyMuPDF must not
# come back: tests/test_para_config.py fails if any requirements file names it, and the hub's
# docker-tool.reusable.yml fails a probed image that has it installed.
pypdfium2>=5.13.0,<6.0
# service/api_client.py — the client script service/README.md tells the user to drive the API
# with. Also undeclared, also surfaced by that test.
requests>=2.34.2
